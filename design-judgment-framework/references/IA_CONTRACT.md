# Information architecture exploration contract (V1.1 additive)

## Scope

Information architecture is distinct from page layout and visual hierarchy. IA covers **entities and relationships, content grouping, navigation and labeling, search/filtering, transitions, and task access**. A screen mockup with tabs does not demonstrate why those tabs are the right categories.

The IA skill runs between precedents and UI options for any structural question. A simple localized interaction may skip only with a recorded reason. Its output is an input to later wireframes, not something retroactively inferred from the chosen screen.

## Required artifact

`ia_exploration`:
- `scope_and_context`: question, domain, job, beneficiary, other users, desired tasks, constraints, knowns and unknowns.
- `information_model`: objects, states, edges/relationships, permissions, cardinality and vocabulary.
- `task_scenarios[]`: persona, entry, goal, edge case, task walkthroughs to compare.
- `alternatives[]` (2–4 meaningfully different structures, 3+ for open IA explorations): organizing principle; canonical objects; parent-child tree or graph; navigation labels; default entry; cross-links; search/filter model; workflow path; non-happy path; tradeoffs; evidence flags.
- `comparison`: selected relative weights, fit rubrics and reasons, per-persona analysis, hard-constraint audit, near ties, sensitivity. Numerical scores must be labeled *estimates*.
- `recommendation`: architecture to prefer conditionally, meaningful exceptions, complementary navigation affordances, causes for a reversal.
- `validation`: tree tests, taxonomy/category studies, task walkthroughs, edge and permission audits; target outcomes and invalidation triggers.

## IA fit scoring, separate from V1 generic sliders

V1.1 supports task-specific IA dimensions through `examples/security-alert-ia.json` plus `scripts/evaluate_ia.py`. This avoids pretending the eight universal decision dimensions can fully represent structural tradeoffs. The option scorer accepts **exactly the dimensions declared in that IA case**. Each weight is 0–100 relative importance; each candidate fit is 0–5. Use `100 * sum(weight * fit/5) / sum(weights)` to create an inspectable estimated ranking. The weights are **not observed user data or scientific priors**.

IMPORTANT: The original preference studio and `scripts/evaluate.py` remain unchanged. IA scores do not automatically sync with org/task preferences in V1.1; integrated domain/persona/IA preference resolution is planned for V2. For a real task, an agent must explicitly explain mapping between the org/task priorities and case-specific IA dimensions. The security example has **task-provided values** for eight axes, not an autogenerated policy.

Prefer to first establish domain evidence and task flows, then score alternatives. Never choose an IA solely because an estimated score wins, especially if user mental model is unobserved or the option depends on unavailable technology (such as reliable correlation).

## Mandatory separation

1. **Structural invariant or hard constraint**: e.g. users must not gain unauthorized access through navigation; gate an alternative, never offset through a positive score.
2. **Priorities**: editable organization/task preferences. Can change ranking, cannot improve evidence quality.
3. **Fit estimates**: human or agent judgments requiring a stated hypothesis and a way to falsify them.
4. **Evidence confidence**: an assessment based on studies, analytics, observation, and contradictory findings, separate from UI sliders.
5. **Risk, reversibility and action authorization**: determined by design governance after IA exploration. A preference ranking does not approve an implementation.

## Review gates and red flags

Return an unresolved IA recommendation and ask for research or explicit review when evidence is thin and consequences are material, when persona priorities cannot be defended, or when cross-permission/object behavior is unknown. Flag:
- category naming without validating vocabulary;
- conflating entity hierarchy with team org chart;
- only one structure shown but described as explored;
- a hybrid that avoids declaring which system owns primary navigation;
- counting made-up clicks or assuming observed behavior;
- optimizing only the happy path or one persona;
- presenting preference-score differences as user-outcome evidence.
